Design the Failure State First

Methodology · May 2026

the happy path is the smaller half of the job

Every model is wrong some of the time. The products that keep their users are the ones that were given something to say at that moment. The ones that lose them were designed entirely around the demo: clean inputs, a confident number, a tidy answer — and no screen at all for the day the data isn’t clean.

The part nobody demos

A demo runs on curated inputs, and curated inputs never arrive in production. What arrives is the kind of input nobody curated: a figure that can’t be matched to its source document, a finding that only just clears the confidence bar, a request the server can’t answer right now. If the interface has no language for those cases, a confident number and a coin-flip look identical on screen — and the user finds out which one they were holding only after they have acted on it.

The lesson isn’t that models are wrong sometimes — every model is. It’s that most interfaces have no language for being wrong. They are designed entirely around the demo: the happy path, the case where the data is clean and the answer is obvious. The cases where the model is uncertain, the inputs are missing, or the world has drifted away from the training set (what a data scientist would call distribution shift) — none of that has a screen unless someone draws it. And that is exactly where a user’s trust either holds or evaporates.

Designing the failure state isn’t error handling. It’s trust recovery. When the system stumbles, the user needs to know why and what to do next. Get that moment wrong and the good answers stop mattering.

So now I start at the bottom

So I changed the order I design in. I no longer start with the case where the model is right. I start with the question almost nobody asks until production forces it: what does this look like when it’s wrong? Low confidence, missing data, a user whose situation the model has never seen — I design those screens first, because they’re the ones that decide whether anyone trusts the good answers later. The patterns library names this the capability contract: what the system is for, where it taps out, and what it hands back to a human. I draw those edges before any happy path. In the private-equity screening product the first state drawn was the abstention: thin evidence renders as “I’m not sure about this one”, kept visible beside the claims that are sure. In the due-diligence dossier it was the confidence bar: a finding that doesn’t clear it never reaches the report, and the report says how many didn’t. In PlanIt it was the error screen itself, in the product’s own words, with the last good answer still on screen underneath.

The reflex everywhere else is to treat the unhappy path as a rounding error. “Edge cases are too rare to be worth it.” They are rare, right up until the day production hands the system something it’s never seen — and by then the trust that took months to build is gone in an afternoon. The happy path is the smaller half of the real work. The rest is the part nobody demos, and it’s the part that decides whether a business will run on what you built.

What I believe now

Every intelligent system I design now opens with one question, asked before a single happy-path screen: “What happens when this fails?” Not as a polish pass at the end. As the first design problem, because it’s the one the user will actually judge you on.
